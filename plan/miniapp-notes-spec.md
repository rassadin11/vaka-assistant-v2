# Спецификация: экран «Заметки» (Mini App, внеплановая задача 2026-10-15)

Контекст исполнителю: самодостаточен вместе с `plan/stage-9.md` (раздел «Ограничения и принципы»), `plan/stage-9-architecture.md` (решения по auth/RLS/API/frontend/cache) и блоком «Принятые архитектурные решения» мастер-плана. Данные — таблица `notes` (`plan/db-schema.md`), существующая логика — `tools/notes.py` (реестр §7c), лимиты — `core/profile.py`, дизайн — `plan/miniapp-design-iteration-1.md` (палитра) и `plan/miniapp-design-iteration-2.md` (скелетоны загрузки).

## Назначение

Третий раздел Mini App рядом с «Календарём» и «Финансами»: тематические заметки, которые пользователь и ассистент ведут вместе. Сейчас заметки доступны только через бота — попросить список, попросить прочитать тему, попросить дописать. Экран делает их обозримыми: список тем за один взгляд, полный текст без пересказа модели и правка руками, без посредника в виде диалога.

## Решения владельца (2026-10-15)

1. **Полный CRUD**, не только просмотр: создать, переименовать, править текст, удалить.
2. **Переименование в занятую тему — честная ошибка**, без молчаливого слияния двух заметок.
3. **Оптимистичная блокировка по `updated_at`**: если ассистент изменил заметку, пока её правили, правка не затирает его дописку молча.
4. **Плоский текст**, переносы строк сохраняются. Markdown не рендерится: модель пишет в `content` простой текст, рендер дал бы расхождение между тем, что видно в боте, и тем, что видно в Mini App.

## Данные

Миграция не нужна. Таблица `notes` уже несёт всё необходимое: `id` (bigint PK), `user_id`, `title` (NOT NULL), `content` (NOT NULL DEFAULT `''`), `created_at`, `updated_at`, `UNIQUE (user_id, title)` и индекс `notes_user_id_updated_at_idx (user_id, updated_at DESC)` — ровно порядок списка.

Адресация в API — по `id`, а не по заголовку: заголовок переименовывается и не годится в URL. Инструменты LLM продолжают адресовать по заголовку, это их контракт и он не меняется.

Лимиты (единый источник — `core/profile.py` и константы, переезжающие в `core/notes_service.py`):

| лимит | значение | где |
|---|---|---|
| заметок на пользователя | 100 (small) / 300 (prod), env `MAX_NOTES_PER_USER` | `profile_limits().notes_per_user` |
| длина заголовка | 64 символа после `_sanitize_title` | `MAX_NOTE_TITLE_LENGTH` |
| длина текста | 8000 символов | `MAX_NOTE_CONTENT_LENGTH` |
| одна дописка инструментом | 1000 символов | `MAX_APPEND_TEXT_LENGTH` |

**`LIST_NOTES_LIMIT = 50` к Mini App не относится.** Это контекстный бюджет модели (S10): `list_notes` отдаёт 50 строк, чтобы не съесть бюджет запроса. Экран показывает все заметки пользователя — 300 строк по заголовку и двум числам стоят килобайты, пагинация не нужна. Исполнителю: не переносить этот cap в webapp.

## UI

### 1. Список тем (главный экран раздела)

- Строка: заголовок; под ним — когда изменено (относительно: «вчера», «3 дня назад», дальше — дата) и размер в символах.
- Порядок — `updated_at DESC, title`, тот же, что у `list_notes`: открыв экран после разговора с ботом, пользователь видит затронутую тему сверху.
- Поиск-фильтр по заголовку — на клиенте, без запроса к серверу (записей ≤300). Регистр не учитывается.
- Кнопка «+» — создать заметку.
- Пустое состояние: короткий текст о том, что заметки можно вести и через ассистента, и здесь.
- Загрузка — скелетоны строк по дизайн-итерации 2, не текст «Загружаем…».

### 2. Экран заметки

- Заголовок, когда изменено, полный текст с сохранением переносов (`white-space: pre-wrap`).
- Действия: «Править», «Удалить». Удаление — с подтверждением, текст подтверждения содержит заголовок.
- Длинный текст скроллится; переход «назад» возвращает к списку с сохранённым фильтром поиска.

### 3. Редактор

- Поле заголовка (лимит 64, счётчик при приближении к лимиту) и `textarea` текста (лимит 8000, счётчик символов).
- «Сохранить» неактивна, пока нет изменений; «Отмена» при наличии изменений спрашивает подтверждение.
- Ошибки сервера показываются в редакторе, введённое не теряется: занятый заголовок (409 `title_taken`), переполнение, достигнутый лимит заметок.

### 4. Конфликт версий

Ответ 409 `stale` на `PATCH` означает: заметку изменили, пока её правили (почти всегда — ассистент через `append_to_note`). Экран показывает баннер «Заметка изменилась, пока вы её правили» и два действия:

- «Показать новую версию» — показать актуальную версию (из поля `note` ответа или перезапросом), свою правку отбросить (подтверждение, если правка непустая);
- «Всё равно сохранить» — повторный `PATCH` без `expected_updated_at`, правка пользователя побеждает.

Молча не делать ни то, ни другое: оба исхода теряют чей-то текст, выбор остаётся за человеком.

## API (webapp, все — под auth 9.1, RLS, rate limit, метрики)

Префикс `/app/api/notes`, установка — `install_notes_routes(app, *, pool, cache, session_secret, metrics)` по образцу `install_finance_routes`. Чужая заметка под RLS невидима, поэтому обращение к ней — всегда 404, никогда 403.

**Конверт ошибок** — существующий, из `webapp/errors.py`: ошибки поднимаются как `WebAppError(status, code, message)` и отдаются как `{"error": {"code": "...", "message": "...", "trace_id": "..."}}`. Коды этого раздела: `title_taken`, `stale`, `notes_limit`, `note_not_found`; `message` — русский текст для пользователя. Своего формата ошибок раздел не вводит.

**Лимит тела запроса.** `WEBAPP_MAX_REQUEST_BODY_BYTES` (глобальный middleware, 413 `request_too_large`) раньше был 8192 байта — он рассчитывался на короткие payload'ы календаря и финансов. Заметки первыми приносят длинный текст от пользователя: 8000 **символов** кириллицы — это ~16 КБ в UTF-8, то есть заметка допустимой длины не проходила вообще (найдено на ручном e2e 2026-10-15, юнит-тесты роутера этого не видели). Дефолт поднят до 65536 байт: он покрывает худший случай (8000 символов по 4 байта плюс заголовок, плюс запас на `\u`-экранирование у сторонних клиентов) и остаётся ничтожным по памяти. Проверка длины текста остаётся символьной и живёт в домене, а не в middleware: 8001 символ должен давать 400 `content_too_long`, а не 413.

### GET /app/api/notes

```json
{
  "notes": [{"id": 12, "title": "Пробежки", "chars": 420, "updated_at": "2026-10-15T09:12:00+03:00"}],
  "notes_total": 7,
  "notes_limit": 100
}
```

- Порядок `updated_at DESC, title`. Без пагинации и без cap (см. выше). `updated_at` — ISO 8601 в таймзоне пользователя (`users.timezone`), как у остальных разделов.
- `notes_limit` — `profile_limits().notes_per_user`, чтобы UI мог показать «7 из 100» и заранее погасить кнопку «+».

### GET /app/api/notes/{id}

`{"id": 12, "title": "...", "content": "...", "chars": 420, "created_at": "...", "updated_at": "..."}`. Нет своей заметки с таким id → 404.

### POST /app/api/notes

Тело `{"title": "...", "content": "..."}` (`content` опционален, по умолчанию `''`). Ответ 201 с телом как у GET одной заметки.

- Заголовок проходит `_sanitize_title` (trim + схлопывание пробелов), затем валидацию: пустой → 400, длиннее 64 → 400.
- Тема уже существует → **409 `title_taken`**, без upsert. Это сознательное отличие от инструмента `upsert_note`, который молча заменяет текст: в диалоге это удобно, а в UI, где пользователь нажал «создать», молчаливая замена чужого текста недопустима.
- Достигнут `notes_per_user` → 409 `notes_limit`.
- Метрика `webapp_notes_created_total`.

### PATCH /app/api/notes/{id}

Тело `{"title": "...", "content": "...", "expected_updated_at": "..."}`; `title` и `content` — оба опциональны, но хотя бы один обязателен.

- `expected_updated_at` присутствует и не совпадает с текущим `updated_at` в БД → **409 `stale`**: стандартный конверт ошибок плюс поле `note` верхнего уровня с актуальной заметкой целиком (`{"error": {...}, "note": {...}}`). `WebAppError` второго поля не несёт, поэтому эта ветка отдаёт `JSONResponse` напрямую — единственное исключение в разделе. Использовать `note` фронт не обязан: перезапрос заметки даёт тот же результат. Поле отсутствует → запись без проверки (ветка «Всё равно сохранить»).
- Переименование в занятую тему → 409 `title_taken` (решение 2). Сравнение — по `UNIQUE (user_id, title)`; смена только регистра собственного заголовка конфликтом не считается.
- `updated_at` обновляется при любой фактической записи; запись, не меняющая ни заголовок, ни текст, `updated_at` не двигает — иначе чистое открытие редактора перетасовывало бы список.
- Метрика `webapp_notes_updated_total`.

### DELETE /app/api/notes/{id}

Ответ 204, повторное удаление → 404. Метрика `webapp_notes_deleted_total`. В `tool_calls_log` не пишется: это не вызов инструмента LLM, а действие пользователя в Mini App (та же граница, что у удаления транзакции в 9.3).

## Общая доменная логика (рефакторинг)

Вынести в `core/notes_service.py` из `tools/notes.py`: константы лимитов и тексты ошибок, `_sanitize_title` / `_validate_title`, резолв заголовка (точный, затем регистронезависимый), подсчёт заметок, upsert, append, чтение, удаление, список. Инструменты переключить на эти функции.

**Поведение пяти инструментов и их тексты ошибок не меняются** — это регресс-контроль: `tests/test_notes.py` (496 строк) обязан остаться зелёным без правок самих тестов. Если тест приходится менять, значит контракт инструмента сломан — остановиться и доложить, а не подгонять тест.

Роутер webapp импортирует только `core.notes_service`; импорт из `tools/` в `webapp/` запрещён (так сделано в календаре и финансах, проверяется на приёмке).

**Блокировка строки при дописке.** `append_to_note` читает текст заметки и пишет склейку. Без блокировки правка пользователя из Mini App, закоммиченная между этим чтением и записью, теряется молча: оптимистичная блокировка `PATCH` защищает пользователя от ассистента, но не ассистента от пользователя. Поэтому в этой ветке резолв заголовка берёт строку под `FOR UPDATE` (`resolve_note(..., for_update=True)`). Для модели ничего не меняется, контракт инструмента тот же. Семантика `upsert_note` остаётся как есть: полная замена текста — это и есть намерение модели, терять там нечего.

## Крайние случаи

- Заметку удалил ассистент, пока она открыта → 404 → вернуться к списку с сообщением «Заметка удалена».
- Пустой `content` допустим (`DEFAULT ''`): тема-заготовка — нормальный случай.
- Заголовок из одних пробелов → 400 (после `_sanitize_title` он пуст).
- Текст ровно 8000 символов — валиден; 8001 → 400.
- Лимит заметок достигнут: кнопка «+» погашена по `notes_total`/`notes_limit`, но сервер всё равно проверяет сам (UI не источник истины).
- Регистр заголовка: инструменты резолвят тему без учёта регистра, поэтому «пробежки» и «Пробежки» для модели — одна заметка, а для `UNIQUE` — две. Создание темы, отличающейся от существующей только регистром, → 409 `title_taken`, чтобы такая пара не возникала через Mini App.

## Тесты (без сети)

- Юнит `core/notes_service.py`: санитайзинг и валидация заголовка, границы лимитов (64/8000/лимит заметок), резолв по регистру, порядок списка.
- Регресс инструментов: `tests/test_notes.py` зелёный без изменений.
- API `tests/test_webapp_notes.py` по образцу `tests/test_webapp_finance.py`: RLS-изоляция на всех пяти эндпоинтах (чужая заметка → 404); 409 `title_taken` на POST и на PATCH-переименовании; 409 `stale` при расхождении `expected_updated_at` и успешная запись без этого поля; 409 `notes_limit`; 204 и повторный 404 на DELETE; `updated_at` не двигается при записи без фактических изменений.
- Фронт `miniapp/src/notes.test.tsx` по образцу `finance.test.tsx`: рендер списка и пустого состояния, фильтр по заголовку, счётчики лимитов, баннер конфликта с двумя ветками, подтверждение удаления.

## Приёмка (живой e2e)

1. Заметка, созданная в Mini App, видна боту: `list_notes` показывает её, `read_note` отдаёт тот же текст.
2. Заметка, созданная через бота, видна в Mini App с тем же текстом и временем изменения.
3. Конфликт версий воспроизвести вручную: открыть заметку в редакторе, попросить бота дописать в неё строку, сохранить → 409 и баннер; обе ветки («показать новую», «всё равно сохранить») дают ожидаемый текст в БД.
4. Переименование в существующую тему → ошибка, обе заметки целы.
5. Удаление из Mini App → бот её больше не видит.
6. Запись в `plan/progress.md` после полной приёмки по регламенту (тесты + e2e + gitleaks).

## Развёртывание

**Экран едет на прод-профиль, не на текущий сервер профиля small.** В `infra/compose.small.yml` сервис `webapp` стоит за `profiles: ["miniapp"]` и выключен по умолчанию: ему нужны ~192 МБ, Caddy и домен, а в бюджете 2 ГБ это оставляет ~50 МБ запаса (§4.4 `plan/small-profile.md`). Включать только после того, как S13 (замер памяти) покажет запас. Разработка и приёмка по пунктам 1–5 ведутся локально на `make dev-up`.
