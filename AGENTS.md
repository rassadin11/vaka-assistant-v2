# Проект: Telegram-сервис персональных ассистентов

Multi-tenant сервис: один бот, общий пул воркеров, изоляция пользователей через PostgreSQL RLS. Стек: Python 3.12, FastAPI, aiogram 3.x, asyncio-воркеры, PostgreSQL 16 + pgvector + PgBouncer, Redis ×2, Alembic, Caddy. LLM — DeepSeek через OpenRouter.

## Инварианты кода (проверяются на каждой задаче)

- Состояние только в Postgres/Redis/S3; gateway и воркеры stateless.
- RLS: каждая транзакция под ролью `app` открывается с `SET LOCAL app.user_id`; session-level SET запрещён (PgBouncer transaction mode). Роли: `migrator` (только Alembic), `app` (рабочая), `service` (BYPASSRLS, только кросс-пользовательские процессы).
- `user_id` никогда не приходит из аргументов LLM — только инжект диспетчером из TaskContext.
- Mutating-инструменты идемпотентны при переигровке (реестр §1.7, ключ `idem:{update_id}:{n}`).
- Тесты не ходят в сеть и не тратят токены: MockLLMProvider / MockSTTProvider.
- Секреты только из Infisical (кроме bootstrap.env); `.env` в репозитории запрещён.
- LLM только через интерфейс LLMProvider; OpenRouter с `data_collection: deny` и allowlist провайдеров из конфига.
- Время: в БД `timestamptz` (UTC); для модели — ISO 8601 в таймзоне пользователя; `users.timezone` всегда явная.
- Миграции обратно совместимы с предыдущей версией кода (expand-contract).

## Конвенции

- Код, идентификаторы, docstrings — английский; тексты для пользователей и плановые документы — русский.
- Монорепо: `gateway/`, `worker/`, `core/`, `tools/`, `webapp/` (backend Mini App), `miniapp/` (frontend Mini App), `embeddings/`, `migrations/`, `infra/`, `tests/`, `evals/`; обзор — [docs/architecture-overview.md](docs/architecture-overview.md).
- Контракты между этапами (envelope очереди, ToolDefinition, LLMProvider) — pydantic-модели в `core/`; менять только с правкой плана.
- Ожидаемые команды после этапа 0–1: `make dev-up` (окружение с нуля), `pytest`, pre-commit (ruff, mypy).

## Роль внешнего исполнителя

Этот файл читают внешние CLI-агенты (в первую очередь OpenAI Codex CLI), которым оркестратор проекта (Claude, см. [CLAUDE.md](CLAUDE.md)) делегирует реализацию по чёткой спеке. Если ты — такой исполнитель:

- Задачу ставит оркестратор самодостаточным промптом; действуй строго в его рамках. Спека — плановые документы (`plan/stage-N.md` с DoD, `plan/db-schema.md`, `tools_registry_v1.md`); если в спеке нет ответа на возникший вопрос — остановись и скажи об этом в отчёте, а не решай молча в коде.
- Твой дифф пройдёт полную приёмку оркестратором по регламенту выше (дифф целиком, ruff/mypy, pytest, gitleaks, живой e2e). Неполная работа — брак: батчи обрабатывай до конца, циклы — по всем элементам, не бросай хвост списка.
- Не трогай без явного указания: плановые документы (`plan/`, `implementation_plan_v1.md`, `tools_registry_v1.md`, `AGENTS.md`, `CLAUDE.md`), конфиги секретов, `.env`-файлы. Секретов в диффе быть не должно.
- В отчёте верни: список изменённых файлов, краткое обоснование решений, все места, где ты отклонился от спеки или не уверен.
- Не запускай вложенные экземпляры себя и других агентов — оркестрация не твоя роль.
